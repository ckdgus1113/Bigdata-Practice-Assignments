# Week 6 관찰

(`bench.build()` 데이터: 바구니 20,000개, 상품 2,000개, support 50)

## Task 1 · A-Priori

- 쌍 {1468, 0}: 1468 → 0은 52/62 = **0.839**, 0 → 1468은 52/13,080 = **0.004**로 비대칭이다. 쓸 만한 주장은 "1468을 사면 0도 산다" 쪽뿐이다.
- 가장 높은 규칙 1468 → 0 (confidence 0.839, **lift 1.28**)은 믿기 어렵다. 0이 바구니의 65%에 들어 있어 기준선이 0.65이고, 독립이면 기대 동시 출현은 40.5번인데 52번(z≈3.1)이지만 빈발 쌍이 6,397개나 되어 우연으로도 나올 수 있는 값이다.
- 상품 2,000개 브루트포스는 카운터 **1,999,000개**, A-Priori는 1패스 후 빈발 상품 1,849개로 후보 **1,708,476개**(실제 생성 820,259개)다. 상품의 92%가 빈발이라 필터 효과가 약하다.

## Task 2 · support를 낮추기

- support 3까지 가도(7.5초, 164 MB, RAM 15.4 GB) 터지지 않았다. 비용이 급해진 곳은 support 100 → 50으로, 메모리가 28.6 → 107.7 MB가 됐다.
- 카운터는 절반 줄일 때마다 ×5.5, ×4.7, ×3.0(support 400 → 50)으로 2배보다 빨리 늘다가, support 25 이하에서는 모든 상품이 빈발이 되어 893,456개에서 멈췄다.
- 답(빈발 쌍)은 절반마다 ×2.4~3.1로 꾸준히 늘었다. support 50에서 답 6,397개에 카운터 820,259개(답당 128개)이므로, "임계값을 조금만 낮추자"는 얻는 규칙에 비해 메모리를 훨씬 더 쓴다.

## Task 3 · PCY

- 버킷은 1,000,003개(소수). 해시되는 쌍이 약 343만 번이라 버킷당 평균 3.4번으로 임계값 50보다 훨씬 낮아 필터가 잘 걸러지고, 결과는 같은 쌍 6,397개에 피크 카운터 **23,356개(97.2% 감소)**다.
- 정직하게 세면 1패스의 버킷 정수 약 100만 개가 기준선 카운터 82만 개보다 많아, 개수로는 메모리를 옮긴 셈이다. 다만 쌍 카운터가 훨씬 무거워 `tracemalloc`으로는 107.9 MB → 16.7 MB다. 기준선 카운터가 버킷 수를 넘는 교차점은 바구니 약 3만 개 근처이고, 바이트로 보면 더 작은 데이터에서 PCY가 이기며 빈발 쌍 수, 버킷 수, 카운터와 버킷의 크기 비율에 달려 있다.
- 버킷을 100,003개로 줄이면 카운터 197,627개(75.9% 감소), 10,007개 이하는 820,259개로 **감소 0%**였다. 버킷당 평균 343번 이상 해시되어 거의 전부 임계값을 넘고, 비트맵이 전부 통과시키기 때문이다.
